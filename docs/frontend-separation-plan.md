# 下一版前后端分离

首期交付一个可独立构建的参与者前端、版本化 API 和两套可切换的主题。沿用 Django、PostgreSQL 和现有答题事务。参与者前端和管理前端分别构建，由网关在各自入口同源代理 API，继续使用 Session Cookie 和 CSRF。管理端的完整替换排在参与者端之后。

## 参与者接口缺口

| 流程 | v1 已有行为 | 下一版要补的边界 |
| --- | --- | --- |
| 首次加载 | `GET /activity` 读取活动并种 CSRF Cookie。Django 模板额外注入参与者和最近答卷。 | 新增 `GET /participant-session`，返回会话和所属届次、进行中及最近答卷摘要、服务端时间，同时种 CSRF Cookie。活动入口不存在时仍能查询已有会话。 |
| 登记、再次进入、退出 | `POST/DELETE /participant-session` 建立或清除会话。 | 复用登记、限流和匹配规则。再次进入成功后读取会话快照。编号和联系方式留在登记请求正文中。 |
| 列板块、换主题 | `GET /activity` 已有届次、活动状态和板块。主题写在模板和样式中。 | 为参与者入口提供版本化的主题标识。切换入口后按会话届次查询历史，只有当前入口届次可新开卷。 |
| 开卷、继续答题、题图 | `POST /attempts` 开卷或返回当前答卷，`GET /attempts/current` 查在途记录，`GET /attempts/{attempt_id}` 查详情，题图按答题项鉴权。 | 前端以会话摘要定位答卷，再用详情取得题干和原截止时间。题图跟随 Session，保持逐卷授权。补齐独立前端的网关路径和缓存规则。 |
| 交卷与结果 | 已有幂等 `PUT /attempts/{attempt_id}/submission`。请求媒体类型、部分错误和 v1 文档有差异。 | 明确 JSON 校验、首次提交、超时、作废、并发重试与返回结果，前端按稳定错误码处理。 |
| 查历史 | `GET /attempts/history` 按会话分页，已提交答卷走详情。 | 保留同届次范围、分页及状态。前端基于详情显示结果，明确已作废或超时记录的详情字段。 |

表中省略 API 路径的版本前缀。现网归档版的接口和部署方式见 [v1 接口说明](frontend-contract.md)。

## 参与者契约

[OpenAPI 3.1 契约](api/participant-v2.yaml) 以 `/api/v2` 为前缀，覆盖会话恢复、交卷、历史列表、答卷详情及其题图。路径版本使校验、错误和响应字段的行为可以独立于 v1 演进。过渡期通过现有 v1 接口登记、退出、读取活动和开卷，两个版本共用参与者 Session。迁移这四个入口时补写它们的 v2 契约。

- 静态页面先读取会话，再读取活动入口。会话无效时显示登记或再次进入。会话有效时优先恢复进行中答卷，否则按最近答卷状态显示结果、超时提示或板块页。按历史入口打开的详情只改变当前视图。
- 会话与答卷归属以服务端为准。活动暂停、关闭或切换入口时，已有会话仍可读取原届次记录，在途答卷仍按原截止时间处理。入口与会话所属届次不同时，界面保留恢复、结果和历史入口，关闭新开卷按钮。管理员对参与者去身份化后，现存参与者会话也必须失效。账户与跨届记录的设计留在后续阶段。
- 浏览器按 `server_time` 和 `deadline_at` 校准倒计时，最终由服务端判断是否超时。草稿继续留在当前标签页，按届次、参与者和答卷隔离。切换主题时使用同一个草稿键，确认退出或切换身份后移除旧身份的草稿。服务端读取答卷可以将过期状态更新为 `timed_out`。
- 提交响应丢失时，以同一答卷 ID 重试或读取详情。只清除已确认提交的草稿。收到 `429` 时按 `Retry-After` 等待，由用户手动重试。目标站的网关和 Django 都需通过契约验收。

## 实施顺序

1. **做通参与者 API。** 先实现会话快照，再从现有服务接出交卷、历史和详情，补齐登记、退出、活动、开卷、题图的 v2 契约与实现。统一参与者错误响应，把逐卷题图权限和新增路径纳入网关验收。服务端验证原截止边界、并发首写、重复交卷、历史分页、会话过期与跨届隔离。
2. **接上独立的参与者前端。** 用 Vue 3、TypeScript、Vite 构建静态产物，通过 OpenAPI 生成的类型或客户端调用 API。把会话、答题状态、草稿、历史与重试集中在前端应用层。先用现有视觉迁移一条完整流程，从登记到交卷、查记录和退出。手机与桌面验收刷新、新标签页、断线重试、题图与旧题下划线显示后，再将网关入口切到静态产物。
3. **用第二套主题检验边界。** 两套主题共用组件状态和 API 客户端。前端主题配置保存标识、版本、品牌文案、字体、色彩、图标与可选角色素材，样式用 CSS 自定义属性与少量展示组件承载。`GET /api/v2/activity` 提供该届次选择的主题标识及版本，客户端遇到未知值时使用内置简洁主题。后台按活动选择主题并记录原值、新值、操作者和时间。两套主题用同一份测试覆盖换肤后草稿、焦点、可读性、计时和交卷行为。
4. **迁管理端。** 把活动状态、答卷查询与审计作为第一批私密管理 API，随后迁身份揭示、导出、作废和题库操作。复用已有事务与权限检查，保持每人独立账号、默认脱敏、敏感操作留痕和公网不可达。管理端完成验收后替换对应模板入口。
5. **独立发行。** 用新数据库和虚构题库做干净安装、备份及恢复演练。发行清单关联 Git 提交、API 契约版本、静态前端和后端镜像摘要、数据库迁移版本、主题版本与验收结果。业务审计继续按届次追溯题库、答卷状态及管理操作。

首期验收以接手同学能从干净 checkout 独立构建参与者前端、启动虚构活动、切换主题并查询一次真实演示答卷为准。跨届账号、多选题和在线编题按各自的业务规则另排。
