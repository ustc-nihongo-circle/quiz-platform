# 管理控制台与 Linux 预发布实施归档

归档时间：2026-08-27

## 报告用途

本文记录参与者纵向里程碑、现场管理控制台和 V 盘 Linux 预发布环境的实施路线、验证结果、已知边界与后续托管待办。它用于复核和接续，不替代代码、ADR、运行手册或 Git 历史。

正式行为以 [项目计划](PROJECT_PLAN.md)、[现场管理控制台参考](ops-console.md)、[Linux 预发布手册](linux-lab-runbook.md) 和相关 ADR 为准。逐项机器证据见 [管理控制台与 Linux 实验验收](validation-ops-lab.md)。

## 目标和范围

本阶段解决两个问题。

1. 把参与者登记、答题、恢复和结果流程扩展成可由现场人员操作的 `/ops/` 控制台。
2. 在外接 V 盘建立与正式 Linux 服务器接近的 Ubuntu 24.04 环境，演练发布、回滚、备份、恢复和安全拔盘。

本阶段没有连接 remote，没有部署朋友服务器，没有修改 DNS，没有使用真实参与者数据，也没有把现役题库或未审查高清主视觉角色放入 Git 或发布包。

## 实施路径

### 1. 固化基线和隐私边界

- 检查 `.gitignore`、暂存区和已跟踪文件，确认 `_private/`、`docs-agent/`、媒体运行数据、密钥和浏览器证据没有进入 Git。
- 在 `main` 建立首个参与者纵向里程碑基线 `f5492dc`。
- 创建 `aster/ops-console-lab`，所有管理控制台和 Linux 演练工作都在该分支推进。
- 发布包只允许从干净提交生成，清单记录完整提交、依赖文件、迁移列表和 SHA-256。

### 2. 完成活动和参与者边界

- 为 `ActivityEdition` 增加唯一的 `is_participant_entry`，参与者入口不再猜测“最新活动”。
- 只有入口届次可以开放。切换入口、活动状态和题库版本都通过事务服务并写入审计日志。
- `paused` 和 `closed` 阻止新登记与新答题，但允许已有身份再次进入、恢复答题和查看结果。
- `start_attempt()` 同时锁定活动和参与者，消除管理员暂停与参与者开始答题之间的竞态。
- 题图改为答题项授权端点，Caddy 不直接公开现役题库媒体目录。

### 3. 建立现场管理控制台

- 使用独立 Django 账号和统一 `quiz.operate_quiz` 权限。生产配置不挂载默认 `/admin/`。
- 使用 `django-axes` 对登录失败限速，管理员 Session 最长八小时并在浏览器关闭时失效。
- `/ops/` 使用服务端模板和少量原生 JavaScript，延续粉青白、深蓝硬边和复古窗口方向。
- 页面提供监控、POST 身份检索、页面级完整字段、CSV 导出、内部榜单、题库切换、兑奖词、作废、去身份化和只读审计。
- 身份导出流式返回，服务器不生成临时 CSV。编号、联系方式、请求正文和导出内容不进入日志。

### 4. 建立提交态 Linux 发布链

- 在 `V:\WSL\Ubuntu-Quiz-Lab` 安装 Ubuntu 24.04，VHDX 上限 160 GB。
- Ubuntu 内使用原生 PostgreSQL 18、Gunicorn、Caddy 和 systemd，不安装第二套 Docker Engine。
- 应用使用无登录 shell 的 `nihongo-quiz` 账号。环境、媒体、备份和恢复目录使用 0700，服务使用 `UMask=0077`。
- 每次发布建立独立源码目录和虚拟环境。迁移、Django check、collectstatic 和数据库就绪检查通过后才切换 `current`。
- PostgreSQL 实际使用 5433，避开 Docker Desktop 开发数据库占用的 5432。

### 5. 用真实演练修正发布缺陷

| 现场发现 | 原因 | 最终处理 |
|---|---|---|
| systemd 无法直接执行备份脚本 | Windows Git 归档导出 CRLF，解释器变成 `bash\r` | `.gitattributes` 强制 Shell 脚本使用 LF，构建器再次检查 ZIP 内容 |
| E 盘副本在 `chmod` 和 `cp -a` 时失败 | NTFS/DrvFs 不支持需要的 POSIX 元数据操作 | Linux 主备保持 0700，异盘副本逐文件写入并依赖 Windows ACL，完整性由 SHA-256 清单判断 |
| 恢复脚本无法新建数据库 | 应用角色按最小权限没有 `CREATEDB` | 恢复演练要求 root，由本机 `postgres` 创建限定后缀的新库，数据仍归应用角色 |
| 恢复后的题库子目录权限过宽 | tar 保留了归档内的默认目录权限 | 应用和备份服务使用 0077 umask，恢复后递归清除 group/other 权限 |
| 发布后导入了虚拟环境中的包而非当前源码 | 发布根目录与 `src/` 布局没有传给 Gunicorn 和管理命令 | `manage.py` 和 systemd 显式加入当前发布的 `src` |
| Windows 浏览器在 WSL 重启后无法访问 18443 | Hyper-V WSL 默认入站为 Block，代理 DNS 返回假 IP | 没有放宽防火墙。最终浏览器证据在 Ubuntu 内完成，Windows 单端口规则保留为用户明确批准事项 |
| 复选框触控区只有 24px | 测试最初只覆盖常规按钮 | 标签点击区改为至少 44px，三视口重新测量 |
| 桌面审计动作名覆盖管理员列 | 长英文动作名不换行 | 审计网格允许任意位置换行并重新截图复核 |

### 6. 完成数据安全和运维演练

- systemd 日备和手工里程碑备份都能生成 PostgreSQL 自定义格式转储、媒体归档、发布信息、迁移状态和 SHA-256 清单。
- V 盘主备与 E 盘忽略目录副本逐项通过哈希校验。
- 两份备份分别恢复到全新 `_restorecheck` 数据库，迁移、对象计数、身份解密和媒体权限通过。
- 应用回滚到前一发布并通过就绪检查，再切回当前发布。
- 终止发行版和完整 `wsl --shutdown` 后重新启动，systemd 服务和数据库数据仍在。
- 停止 Ubuntu、Docker Desktop 和全部 WSL 后，V 盘只读移除预检返回通过。脚本没有自动脱机磁盘。

- PostgreSQL 18：8 项并发测试通过。

- Linux Playwright 1.62.0 / Chromium 151 覆盖 1440×900、390×844 和 360×800。
- 登录、监控、检索、完整字段、刷新复位、两类 CSV、活动状态、题库切换、兑奖词、作废和去身份化通过。

## 为最终托管仍需完成的工作

### A. 本地实验收尾

- [ ] 人工创建日常 Linux 管理用户并设置独立密码，再授予 sudo。应用账号继续保持无登录 shell。
- [ ] 复核两个恢复检查库和媒体目录，确认保留的三份备份仍通过 SHA-256 后再删除恢复检查数据。
- [ ] 只有确需从 Windows 浏览器访问实验站点时，才单独评审 TCP 18443 的 Hyper-V WSL 规则、动态地址映射和 Caddy 根证书信任。它们不是朋友服务器上线的前置条件。

### B. 源码与发布治理

- [ ] 决定 `aster/ops-console-lab` 如何进入长期主分支。合并前重新检查私密路径和发布资产。
- [ ] 建立 GitHub Organization 或其他私有协作仓库，经用户确认后再连接 remote。
- [ ] 为 SQLite、PostgreSQL 18、Ruff、Django check、迁移检查和 collectstatic 建立 CI。PostgreSQL 缺失时必须失败。
- [ ] 规定发布 tag、批准人、发布清单、哈希保存位置和回滚保留数量。服务器只安装获批提交生成的包。
- [ ] 启用依赖更新、秘密扫描和基础代码安全检查。任何扫描结果都不得上传现役题库或私密部署资料。

### C. 收集朋友服务器事实

在接触服务器前，需要服务器维护者确认以下事实。不要索要或在聊天中粘贴私钥、密码和完整配置文件。

- [ ] 服务器地区、发行版、版本、CPU 架构、内存、可用磁盘和时间同步状态。
- [ ] 是否能提供独立 Linux 用户、sudo 或受控安装协助，以及 SSH 公钥接入方式。
- [ ] 公网 80/443 是否可用，当前防火墙、云安全组、反向代理和其他站点是否占用端口。
- [ ] PostgreSQL 由本机安装还是使用托管服务，可用版本、备份责任和恢复权限归谁。
- [ ] 可用子域名、DNS 控制人、解析变更窗口，以及服务器所在地对应的备案和接入要求。
- [ ] 异机备份目标、容量、保留期限、加密方式和谁能执行恢复。
- [ ] 活动当天维护人、可响应时间、重启权限和故障升级联系人。

事实不完整时只做服务器预检，不上传现役题库，不创建真实参与者，不修改 DNS。

### D. 生产安全设计

- [ ] 决定 `/ops/` 的第二道保护。当前有独立账号、密码、Session 和登录限速，但没有 MFA。上线前应选择 TOTP MFA、VPN/反向代理访问门槛或等效方案，并验证现场可用性。
- [ ] 在目标机生成新的 Django、AES-GCM 和 HMAC 密钥，绝不复用实验环境值。
- [ ] 为密钥建立独立恢复副本。数据库备份不包含密钥，没有 AES-GCM 密钥就无法恢复身份字段。
- [ ] 建立生产环境变量、文件权限、轮换负责人和紧急吊销流程。
- [ ] 明确参与者隐私告知、资料用途、管理员范围、人工去身份化流程和活动结束后的保留决定。
- [ ] 完成现役题库的来源、事实和答案审核。若使用旧库例外，记录批准人、理由和时间。
- [ ] 只发布许可清单标记为 `cleared_for_public_web` 的素材。高清主视觉角色继续禁止进入发布包。

### E. 服务器预发布

- [ ] 使用虚构数据在目标机建立独立系统用户、目录、PostgreSQL、Gunicorn、Caddy 和 systemd。
- [ ] 应用只监听回环地址。代理覆盖转发头后才启用 `SECURE_PROXY_SSL_HEADER`。
- [ ] Caddy 只提供 collectstatic 产物。题图继续经过 Django 授权端点。
- [ ] 使用正式候选域名取得公共 TLS 证书，验证安全 Cookie、CSRF、登录限速和代理头。
- [ ] 配置应用日志、Caddy 日志、journal 保留和磁盘告警，确认不记录身份明文、题干、答案和请求正文。
- [ ] 建立异机备份并恢复到全新数据库。只看到备份成功不算通过，必须完成恢复演练。
- [ ] 在目标服务器重跑 50 路 HTTPS、三视口浏览器和发布回滚。V 盘成绩不能代替目标机容量验证。
- [ ] 准备存活、就绪、证书到期、备份失败、磁盘空间和数据库连接告警。

### F. 上线批准和活动运行

- [ ] 每名操作员创建独立账号并通过实际设备登录。不要共享管理员账号。
- [ ] 确认活动届次、参与者入口、题库版本、抽题配额、兑奖词和状态切换人。
- [ ] 在导入现役题库和开放活动前分别建立里程碑备份。
- [ ] 确认 DNS TTL、切换时间、回退地址和维护人在场，再修改 DNS。
- [ ] 首次公网 HTTPS 验证后从 300 秒开始逐步提高 HSTS。未经域名所有者同意，不启用子域 HSTS 或 preload。
- [ ] 活动当天保留发布回滚命令、数据库恢复路径、暂停入口和维护人联系方式。
- [ ] 活动关闭后建立快照，按组织决定去身份化。删除身份后，人工处理仍包含旧身份的备份。

## 下一次接续建议

最有价值的下一步不是继续改代码，而是取得朋友服务器的事实清单。信息齐全后再决定服务器部署拓扑、`/ops/` 第二道保护、异机备份位置和上线窗口。

在用户明确授权前，Agent 只做只读服务器清单分析、配置候选、发布包预检和操作单，不登录外部服务器，不连接 remote，不修改 DNS，也不处理真实参与者资料。
