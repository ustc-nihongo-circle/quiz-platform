# 归档基线容量实测

2026-09-13，以原活动运行版本 records-20260912 在隔离、纯虚构数据环境测试。**最大已验证稳定档位为 20 位同步答题参与者；50 位同时操作时延迟不达标。** 这不是理论上限，也不能换算成网站日访问量或空闲在线人数。30 人探索未满 15 分钟，因本轮收尾范围停止，不计入稳定容量或失败档位。

## 条件与口径

应用 1 CPU / 512 MiB、PostgreSQL 0.5 CPU / 512 MiB，原版本 2 个同步 Gunicorn worker。使用原共享服务器的隔离数据库，原正式 Web/DB 始终停止。378 道合成题、7 栏目、28 题图引用，每次 15 题，每题 1 分。20 人每 75 秒同步开卷，读取题图，等待 20 秒后集中提交、原样重复提交，再读历史第一页，共 12 轮、900 秒、240 份完整答卷。

全部客户端共享一个出口 IP，保留原应用和 Nginx 限流策略。流量经过回环 HTTPS，不包含真实校园网络与公网尾程。稳定档的身份进入复用之前创建的合成账户，首次登记集中操作在 50 人探测中覆盖，不把恢复身份性能当新登记容量。

稳定标准：持续 15 分钟、非预期错误低于 0.1%、读取/开卷 P95 ≤ 2 秒、交卷 P95 ≤ 3 秒、无成绩错误。20 人档所有观测请求均成功，未遇到 429；240 份答卷及重复提交均返回 15 分。50 人探测同样无请求失败或成绩错误，但开卷和交卷 P95 超标，因此提前停止，不算通过 15 分钟测试。

## 结果

单位为秒。

| 操作 | 20 人档请求数 | 20 人 P95 / P99 | 50 人 P95 / P99 |
| --- | ---: | ---: | ---: |
| 进入/恢复身份 | 20 | 0.168 / 0.174 | 0.587 / 0.597 |
| 开卷 | 240 | 1.630 / 1.816 | 3.161 / 3.292 |
| 交卷 | 240 | 1.566 / 1.870 | 4.244 / 4.441 |
| 重复交卷 | 240 | 1.104 / 1.293 | 2.550 / 2.704 |
| 历史第一页 | 240 | 0.305 / 0.362 | 0.663 / 0.677 |
| 题图 | 291 | 0.251 / 0.284 | 0.795 / 0.819 |

20 人档记录 1271 次业务请求，平均 1.41 次/秒（含轮次间等待）。50 人档只有一轮、约 34 秒，不能与持续吞吐直接等同。

稳定阶段前 890 秒采样显示：应用 CPU 峰值 104.98%、内存占配额峰值 22.50%；数据库 CPU 峰值 24.99%、内存占配额峰值 29.48%；观测数据库连接峰值 2、锁等待峰值 0。CPU 以一个逻辑核为 100%；采样会漏掉短时峰值，不能凭这些数字断定唯一瓶颈。

## 使用建议与边界

在相同原配置下，集中开卷/交卷暂按每批 15–20 人安排，留出共享服务器和网络余量。这是基于实测的保守建议。已测试的未达标档位是 50 人，20 至 50 人之间的准确边界未继续逼近。

本次冻结活动归档版本，不为容量探索改写已封存版本。归档部署包使用相同业务源码及固定依赖，并增加代理服务地址识别与通用部署工具；其 Caddy 拓扑及线程配置与原部署不同，不能直接把此报告当作所有新部署的承载保证。后台刷新、历史第二页之后、跨出口 IP 对照与优化复测留待下一版同条件评估，不在本报告中声称已验证。

原始汇总见 [capacity-v1.json](capacity-v1.json)，探针见 [burst_probe.py](../tests/performance/burst_probe.py)。所有真实活动数据和备份均未用于施压。
